검증 기반 · 문서 1 G04~G06, G10

실패를 잡아내는 검증 절차를 만듭니다

기존 검증 도구를 우선 사용합니다. 부족하면 프로젝트에 맞는 검증 스크립트와 그 사용법을 담은 짧은 스킬을 만듭니다.

만들거나 보완할 파일

  • scripts/verify-unity.ps1
  • .agents/skills/verify-my-game/SKILL.md
  • 계약 예시와 실행 보고서 형식

반드시 실패시켜 볼 조건

  • 종료 코드 0인데 XML이 없거나 테스트 0개
  • 필수 case가 빠지거나 후보가 달라짐
  • 빌드 파일이 없거나 Player가 실행되지 않음
완료 증거: 정상 실행을 통과시키고, 의도적으로 잘못 만든 fixture를 거부한 로그. 스크립트 이름만 생긴 상태는 미완료입니다.
Codex에 복사할 요청문 · 최소 검증기
확인한 기존 테스트·빌드 도구를 재사용해서 이 프로젝트의 최소 검증 절차를 구현해줘.
문서 1 G06/G10에 맞춰 compile, EditMode, 필요한 PlayMode, Player build와 smoke 결과를 구분해줘.
종료 코드만으로 PASS를 내지 말고 XML 누락·0개 테스트·필수 case 누락·오래된 증거·빌드 누락을 검출해줘.
실제 검사한 후보 내용과 결과를 연결하고, 실행할 수 없는 검사는 미완료로 보고해줘.
검증 스킬에는 이 절차를 안내하는 짧은 사용법을 작성해줘. 보호된 설치 경로는 우회하지 말고 적용 방법을 알려줘.

첫 게임 작업 · 문서 1 G04~G09

작은 기능 하나를 계약하고 끝까지 만듭니다

첫 기능은 변경 파일과 수용 조건을 쉽게 설명할 수 있는 것으로 고릅니다. 예를 들어 대시를 고른다면 지상 입력·공중 입력·재사용 대기시간의 기대 동작을 먼저 적습니다.

작업 계약에 넣을 것

  • 목표와 이번에 하지 않을 범위
  • 허용 파일과 보호할 검증 기준
  • 수용 조건·필수 검사·사람 플레이 확인

AI가 연속 수행할 것

  • 허용 범위의 구현 → 시험 → 수정
  • 총 시간·수정 횟수 한도 확인
  • 기능이 준비되면 후보 고정과 최종 검사
완료 증거: 고정한 후보, 모든 필수 기계 검사, 실행 가능한 빌드. 범위를 늘려야 하면 새 계약을 만듭니다.
Codex에 복사할 요청문 · 대괄호를 채운 뒤 사용
다음 작은 기능을 구현해줘: [구체적인 기능 목표].
허용할 파일/영역은 [경로]이고, 성공 조건은 [관찰 가능한 조건]이야.
문서 1의 작업 계약으로 목표·비목표·필수 검증·시간 및 수정 상한을 정리한 뒤, 이미 허가된 범위에서 구현·시험·수정을 계속해줘.
기존 사용자 변경과 검증 기준을 보존하고, 새 후보에는 새 검증 결과를 남겨줘.
검사되지 않은 항목을 PASS로 쓰지 말고, 마지막에 실제 빌드와 플레이 확인 방법을 전달해줘.
Git 쓰기·범위 확대·외부 출시·새 의존성은 이 요청의 허가에 포함하지 않아.

사람의 판단 · 문서 1 G06~G09

플레이하고, 전달할 결과를 확정합니다

기계 검사는 정확한 게임 의도와 재미를 대신하지 않습니다. 보고서가 가리키는 동일 빌드를 직접 실행하고 조작감과 기능의 의도를 확인합니다.

검토할 내용

  • 변경 범위와 실제 테스트/빌드 결과
  • 플레이한 빌드의 버전과 미해결 사항
  • 게임 목표에 맞는지, 재작업이 필요한지

결정할 내용

  • 패치·빌드 전달로 마칠지
  • 정확한 Git 동작을 별도로 허가할지
  • 범위 내 재작업 또는 새 계약이 필요한지
완료 증거: 사람 플레이 기록과 납품 결과. 검증 성공은 Git 통합이나 외부 출시 허가를 자동으로 뜻하지 않습니다.

관찰 · 문서 1 G09 / 문서 2 S02

5~10개 작업에서 반복되는 손실을 찾습니다

실패·취소·재시도도 기록합니다. 비용을 알 수 없으면 모른다고 적고, 사람이 실제로 쓴 시간과 단순 대기 시간을 구분합니다.

작업마다 남길 내용

  • 시작/종료 상태, 실패 원인, 수정 횟수
  • 총비용의 실측/추정/미확인 구분
  • 사람 활동 시간, 후속 결함, 플레이 결과

선정할 개선 문제

  • 반복되는 손실과 실제 사례
  • 원인 가설과 그 가설이 틀릴 가능성
  • 바꾸지 않는 대안과 최소 변경 범위
완료 증거: 작은 후보로 시험할 수 있는 병목 하나. 중대한 검증·안전 오류는 5건을 기다리지 않고 수리합니다.
Codex에 복사할 요청문 · 개선 후보 선정
문서 2 S02~S06을 읽고, [실행 기록 경로]에서 반복 손실을 분석해줘.
실패·취소·재시도와 개선 자체의 비용을 포함하고, 모르는 비용은 0으로 처리하지 마.
관측 근거, 원인 가설, 반대 가설, 실패 시나리오, 개선하지 않는 대안을 비교해서 작은 후보 하나를 추천해줘.
캐시나 다중 에이전트를 미리 정답으로 고르지 말고, 가장 큰 실제 손실부터 판단해줘.
운영 스킬·검증 기준을 바로 바꾸지 말고 후보 범위와 비교 계획을 먼저 구체화해줘.

첫 개선 · 문서 2 S03~S06, S09

별도 후보를 시험하고 제한적으로 도입합니다

이 단계에서 workflow-lab을 시작합니다. 후보 스킬을 게임의 활성 스킬에 바로 연결하지 않고, 검토된 버전을 다음 작업에 적용합니다.

후보를 시험할 때

  • 변경할 요소와 고정할 요소를 구분
  • 같은 과제 계열로 기준선/후보 짝 비교
  • 정상·실패·stale 결과·권한 경계 확인

도입 전에 사람이 확인할 것

  • 정확한 버전·적용 작업군·기간
  • 비용과 품질의 남은 불확실성
  • 이전 버전 보존과 중지·복구 방법
완료 증거: 비교 보고서와 제한 도입/보류/거절 결정. 도입했다면 관찰 후 유지·확대·복구를 판단합니다.
Codex에 복사할 요청문 · 별도 후보와 검토 패키지
선정한 개선안 [제안 ID/내용]을 workflow-lab의 후보 파일에서 구현하고 시험해줘.
문서 2에 따라 기존 운영 버전, 후보, 평가 기준을 구분하고 변경 요소와 통제 요소를 비교 계획에 적어줘.
정확성·회귀·실패 검출을 먼저 확인하고, 제한 도입 판단용 관찰과 통계적 효과 입증을 구분해줘.
실패와 재시도 비용을 포함한 보고서, 정확한 후보 버전, 적용 범위, 이전 버전 복구 방법을 준비해줘.
운영 스킬 교체·Git 쓰기·권한 확대·외부 배포는 별도 허가 전까지 수행하지 마.

체크 상태만 브라우저에 저장합니다. 프로젝트 파일·계정·실행 로그에는 접근하지 않으며 외부로 전송하지 않습니다.

사람이 정할 것과 실패 시 다음 행동

계약 안의 반복 실행은 AI에 맡깁니다. 목표·범위·권한·통합·출시는 검토 가능한 결과를 보고 결정합니다.

AI가 계속 수행할 일사람의 판단이 필요한 경계
허용 파일 구현·관련 시험·수정·증거 수집게임 방향·수용 기준·허용 파일·예산 확대
고정된 검증 절차 실행과 실패 원인 조사평가기·정책·활성 스킬·권한 변경
후보와 보고서, 복구 계획 준비Git 쓰기·운영 적용·외부 업로드·출시·새 의존성
폴더 분리와 lock 파일은 서로 다른 역할입니다. 별도 저장소는 이력과 책임을 나눕니다. lock은 기대 버전을 기록합니다. 실제 접근 차단과 증거 보호는 계정·sandbox·도구 권한을 시험해야 확인할 수 있습니다. MVP의 수동 재실행은 강한 격리 보장과 구분합니다.

상황을 선택하면 올바른 다음 행동을 볼 수 있습니다

RUNNING→VERIFYING→REVIEW_READY

필수 기계 검사를 통과하면 사람이 볼 준비가 된 상태입니다. 필요한 플레이 확인과 전달 결정을 거쳐 CLOSED로 끝냅니다. 기계 검사 통과만으로 자동 통합하지 않습니다.

막힌 지점다음 행동
Unity 라이선스·모듈·패키지 준비 부족환경 원인을 기록하고 준비를 마칩니다. 코드 수정 반복으로 숨기지 않습니다.
XML 없음, 0개 테스트, 오래된 빌드PASS를 거부합니다. 실행·증거 연결을 고친 뒤 같은 후보를 다시 검증합니다.
통계가 불확실하거나 비용을 모름효과 입증을 보류합니다. 제한 도입 여부는 별도 범위·근거·승인으로 판단합니다.
개선 도입 뒤 회귀·취소·복구 불명확신규 후보 사용을 중지하고 기준 버전으로 복구합니다. 확인할 수 없으면 MANUAL_RECOVERY로 남깁니다.
04 /

“작동한다”와 “효과가 입증됐다”를 나눕니다

간단한 버그 수정, 현재 작업군의 도입 판단, 모집단에 대한 효과 주장은 필요한 증거가 다릅니다.

EVIDENCE 01

정확성 확인

정상·실패·회귀 시험으로 명세대로 작동하는지 확인합니다.

“이 실패를 검출하도록 고쳤다.”

EVIDENCE 02

파일럿 도입 판단

작은 짝 비교, 비용·사람 시간, 복구 가능성을 보고 제한적으로 사용합니다.

“이 작업군에서 써 볼 근거가 있다.”

EVIDENCE 03

통계적 효과 입증

모집단·표본·지표·판정·예산을 먼저 정하고 독립 데이터로 확인합니다.

“사전 정의한 효과 주장을 지지한다.”

이번에 고친 통계 오류와 해석
구분계산·관찰올바른 해석
기존 6개 층 × 5개최선 결과의 품질 차이 하한도 약 −33.17%p−5%p 기준을 어떤 결과도 통과할 수 없는 계획 오류
최소 MVP의 5~10건실제 손실·비용·사람 시간·회귀 관찰병목 탐색과 제한 도입용. 일반적인 효과 입증 아님
새 F1의 가상 사례86쌍 모두 양쪽 성공, 60쌍에서 10% 이상 절감 → 품질 하한 약 −4.9677%p, 효율 비율 하한 약 0.58917통과 가능한 계산 예. 86건이 권장 표본 수나 검정력 보장이라는 뜻은 아님

F1은 “과제의 절반을 넘는 비율에서 양쪽 성공과 10% 이상 절감”을 다룹니다. 평균 비용 10% 절감을 증명하는 검정은 아닙니다. 실제 확인 실험에는 독립성·표집·가능성·공동 검정력·전체 비용 검토가 필요합니다. 세부 규칙은 문서 2 S07을 따릅니다.

초기에는 좋은 기록이 먼저입니다. 실패와 재시도를 빼지 않고, 총비용·사람 활동 시간·후속 결함을 함께 남기세요. 캐시 hit, 생성 코드량, AI 호출 수만으로 개선 성공을 판단하지 않습니다.
05 /

장기 설계는 필요가 확인될 때 구현합니다

감독하의 최소 MVP를 계속 사용하는 것도 유효한 운영 방식입니다. 자율성은 실제 검증한 경계에 맞춰 높입니다.

지금 시작할 것추가할 수 있는 장기 기능추가할 조건
작업 계약과 실행 보고서상태 DB·요청 멱등성·예산 예약수동 재시작·조정 비용이 반복적으로 큼
고정 검증 절차와 사람 확인격리 워커·보호 오라클·외부 증거 수집무인 실행 필요 + 실제 권한/조작 시험 통과
검토된 버전의 수동 적용정확한 승인 원장·자동 통합·단계별 도입stale 승인·응답 유실·중복 효과 처리 확인
이전 버전 보존과 수동 복구독립 Watchdog·자동 기준선 전환후보를 중지시켜도 복구하는 실제 훈련 통과
작은 파일럿과 정직한 보고비공개 확인 평가·사전등록 통계일반화된 효과 주장 필요 + 검정력·예산 확보

다음 확장 전에 세 가지를 확인하세요. 어떤 손실이 반복됐는가, 이 기능이 어떻게 줄이는가, 추가 구축·운영 비용을 감당할 근거가 있는가. 게임 진척 없이 시스템 기능만 늘면 범위를 다시 정합니다.
