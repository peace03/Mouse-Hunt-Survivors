# Unity 검증

현재 실행기는 Unity `6000.6.0f1`, Windows 64bit 개발 빌드를 지원합니다. 명세는 원문 게임 개발 설계서 G04·G06·G10, 실행 기준은 [unity-plan.json](Verification/unity-plan.json)입니다.

## 새 작업

1. 변경 전에 저장소·브랜치·사용자 변경을 읽습니다.
2. 저장소 루트에서 기준선을 만듭니다. 이미 있는 파일은 덮어쓰지 않습니다.

```powershell
python -B Workflow/Tools/verify_unity.py --snapshot Workflow/Tasks/<task-id>/baseline.json
```

3. [작업계약 양식](Templates/작업계약.json)을 같은 폴더의 `contract.json`에 복사합니다. 실제 목표·경로·수용 조건·한도를 작성하고 `base_oid`와 출력된 `base_manifest_digest`를 넣습니다. 실제로 채운 뒤에만 `example_only`를 `false`로 바꿉니다.
4. 허가된 구현과 관련 시험을 진행한 뒤 실행합니다.

```powershell
python -B Workflow/Tools/verify_unity.py --contract Workflow/Tasks/<task-id>/contract.json
```

Editor 설치 위치가 다르면 `--editor "설치경로/Editor/Unity.exe"`를 붙입니다. 프로젝트 버전은 바꾸지 않습니다. 시간 한도는 계약의 `max_wall_minutes`이며 실행기는 자동 재시도하지 않습니다. 재시도는 첫 실패를 보존한 새 run으로 만들고 전체 작업 상한을 사람이 관리합니다.

## 실행과 증거

매 실행마다 `Runs/<UTC시각>-<ID>/`를 새로 만듭니다. 원본 `Assets/Packages/ProjectSettings`의 Git 관리 대상 및 미추적 파일을 복사하고, [UnitySupport](Verification/UnitySupport/)를 사본에만 넣습니다. 원본 Unity 에셋이나 설정을 저장하지 않습니다. `Library`는 공유하지 않습니다.

Unity/URP의 첫 빌드는 렌더링 설정과 셰이더 필터 값을 직렬화합니다. 먼저 준비 빌드를 실행하고 같은 scripting define 집합의 저장 순서를 정렬한 뒤, 계획의 `preparation_writes`에 명시한 5개 파일만 바뀌었는지 확인합니다. 변경 전후 해시를 `preparation-changes.json`에 남긴 뒤 실제 사본의 입력을 동결하고 모든 gate를 새로 실행합니다. 이 목록 밖의 변경은 거부합니다. 준비 빌드는 납품 빌드로 사용하지 않습니다. 동결 뒤 소스·설정 변화도 계속 실패로 처리합니다.

| gate | 확인하는 증거 |
|---|---|
| scope | 시작 기준선 대비 추가·수정·삭제와 허용/보호 범위, 실행 전후 내용 동일성 |
| compile | 정확한 Editor에서 실행된 컴파일 완료 메서드와 후보·nonce가 일치하는 보고 |
| editmode | 새 NUnit XML, 실제 case·총수·필수 case, 실패·skip 없음 |
| playmode | 첫 빌드 씬 로드·프레임 진행·활성 카메라 테스트와 XML |
| player_build | BuildReport 성공, 지정 target·scenes, exe·DLL·Data와 전체 파일 해시 |
| player_smoke | 실제 Player 실행, 첫 씬·60프레임·오류 0건·그래픽 장치·정상 종료, 동일 빌드 |

현재 지원 테스트 3개는 빌드 씬 존재·Missing Script·기본 시작 동작을 확인합니다. 게임 기능의 입력·수치·승패는 별도 프로젝트 테스트를 추가해야 합니다. 계획의 필수 case 목록은 기능 후보가 임의로 줄이지 않습니다. 프로젝트 테스트가 있으면 함께 실행하며 실패·skip을 숨기지 않습니다.

XML과 증거가 없거나 비었을 때, 종료 코드만 0일 때, 실행·후보가 다를 때 PASS를 내지 않습니다. 로그·XML·프로세스 인자·보고서·빌드를 보존합니다. 실패 후 성공한 재시도로 첫 실패를 지우지 않습니다.

## 판정과 사람 확인

`report.json`의 `machine_result`와 `result`를 구분합니다. 기계 검사가 모두 통과해도 사람이 플레이해야 하는 계약은 `state=REVIEW_READY`, `human_playtest=pending`, `result=INCONCLUSIVE`로 남습니다. 실행기 종료 코드 0은 기계 검사 통과를 뜻하며 납품·출시 승인이 아닙니다.

[플레이 확인 양식](Templates/플레이확인.md)에 `build_digest`, 시나리오, 관찰과 판단을 작성합니다. 자동 시작 확인은 조작감·재미·외형·모바일·성능 검증을 대신하지 않습니다.

## 실행기 자체 검사

```powershell
python -B -m unittest discover -s Workflow/Tools -p "test_*.py"
python -B Workflow/Tools/check.py
```

Python fixture 검사는 정상/누락/0개/실패/skip XML, 필수 case, 범위, 경로, 후보·nonce, 산출물, 사람 확인 대기를 시험합니다. 실제 Unity 컴파일 오류 검출은 별도 복사본의 고의 오류로 확인하고 게임 원본에는 오류를 넣지 않습니다.

검증기·계획·지원 코드·활성 스킬 변경은 별도 개선 작업입니다. 검토한 파일의 해시로 `workflow.lock.json`을 새 릴리스에 맞춰 갱신하며 실패를 덮기 위해 lock을 자동 재생성하지 않습니다.

## 한계와 보존

현재 방식은 같은 Windows 계정에서 실행하는 `supervised_local`입니다. 복사본과 해시가 악성 후보 코드의 접근을 차단하거나 XML의 진실성을 보증하지는 않습니다. 무인 운영·모바일·배포·강한 격리는 원문 B부의 별도 구축 대상입니다.

`Runs/`는 새 실행마다 소스·Library·빌드가 생겨 디스크를 사용합니다. 사용자 확인 후 보존할 보고서·원시 증거·빌드를 확보하고 해당 실행 폴더만 정리합니다. 실행기는 기존 기록을 자동 삭제하지 않습니다.
