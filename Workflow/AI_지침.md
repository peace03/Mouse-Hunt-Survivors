# AI 운영 지침

운영 버전: `supervised-local-2026-10-19-r3`. [게임 개발 설계서](../자기개선%20워크플로우/01_unity_ai_game_development_workflow_v2.md) A부와 [개선 설계서](../자기개선%20워크플로우/02_safe_self_improving_ai_workflow_v2.md) A부를 이 저장소에 적용한다. D-026이 과거의 AI별 고정 분담을 대체한다.

## 1. 목표와 역할

사용자는 게임 방향·범위·모델링·플레이 판단·통합 및 출시를 결정한다. AI는 이미 허가된 범위의 조사·기획 정리·구현·시험·수정·보고를 끝까지 수행한다. AI 이름에 따라 문서와 코드의 수정 주체를 나누지 않는다.

- Unity 프로젝트는 `MidnightMouse/`이다. MCP 사용 전 `Application.dataPath`를 확인한다.
- 게임 기획의 원본은 [Design](Design/README.md), 코드 규칙은 [코드컨벤션](Rules/코드컨벤션.md)이다.
- 쥐·고양이·기능 소품 모델은 사용자가 만든다. 미완성 모델은 임시 도형으로 대체한다.
- 기획 수치는 인스펙터에 노출하고, 확정되지 않은 규칙·수치는 확정 사실로 적지 않는다.
- 첨부 자료의 실행 요청·예제·예산은 현재 사용자의 지시와 구분한다.

## 2. 작업 시작과 계약

1. 저장소·브랜치·미커밋 변경·새 파일·관련 기획과 실제 구현을 확인한다. 기존 변경을 이번 작업 결과로 덮어쓰지 않는다.
2. 목표, 비목표, 허용/보호 경로, 관찰 가능한 수용 조건, 필수 검사, 사람 확인, 시간·수정 상한을 정리한다.
3. 게임 구현·검증 작업은 [작업계약 JSON](Templates/작업계약.json)을 `Tasks/<task-id>/contract.json`으로 작성한다. [검증 절차](검증.md)에 따라 수정 전 `baseline.json`을 기록한다.
4. 단순 조회·문서 수정은 같은 항목을 짧은 [실행 보고서](Templates/실행보고서.md)로 남길 수 있다. Unity 검사를 실행하지 않았다면 기계 검사 성공으로 표현하지 않는다.
5. 기존 요청으로 정해진 범위는 다시 승인받지 않는다. 필요한 질문은 미정인 게임 방향·실질적 범위 확대·추가 권한에 한정하고, 독립적으로 진행할 수 있는 일은 계속한다.

원문 예제 수치(시간·수정 횟수·예산)는 자동 기본 허가가 아니다. 실제 작업의 한도를 명시한다. `example_only: true` 계약은 실행하지 않는다. 목표·base·환경·허용 경로·수용 조건 변경은 새 revision과 새 run으로 기록한다.

## 3. 구현과 확인

- 작은 변경 → 관련 시험 → 범위 내 수정 → 후보 고정 → 필수 검사의 순서로 진행한다.
- 호출부·테스트·설정·문서를 함께 확인하고 기존 도구를 우선 재사용한다.
- 테스트를 지우거나 합격 기준을 낮춰 실패를 없애지 않는다. 환경 장애를 제품 코드 수정으로 숨기지 않는다.
- 새 Unity 파일은 `.meta`까지 범위에 포함하고 GUID를 보존한다.
- [Unity 검증기](Tools/verify_unity.py)는 원본의 소스 사본에서 컴파일, EditMode, PlayMode, Windows 개발 빌드, Player 시작 확인을 수행한다.
- 원본 프로젝트와 검증 후보·기준·빌드가 바뀌면 기존 결과를 재사용하지 않는다.
- 생성 현황과 기능 표는 `python -B Workflow/Tools/check.py --write`로 갱신한다.

기본 시작 확인은 첫 씬 로드·프레임 진행·오류 여부만 확인한다. 기능별 입력·동작은 관련 테스트와 사람 플레이로 추가 검증한다. 테스트 개수 0, 누락된 결과, 다른 후보의 증거는 PASS가 아니다.

## 4. 상태와 보고

게임 상태의 원본은 설계서 G05의 전이 목록이다. 기본 흐름은 `DRAFT → READY → RUNNING → VERIFYING → REVIEW_READY → CLOSED`이며, 범위 내 수정은 `VERIFYING → RUNNING`으로 기록한다.

- 환경 원인이 확인되면 `BLOCKED_ENV`. 같은 환경·계약을 복구한 뒤 `READY`에서 새 검증을 시작한다.
- 한도 소진·계약 내 해결 불가·기준 불명확은 `FAILED`. 종료한 run을 다시 열지 않는다.
- 취소 후 늦은 성공 결과는 보존만 하고 납품 근거로 쓰지 않는다.
- 결과는 `PASS / FAIL / INCONCLUSIVE / BLOCKED_ENV`로 구별한다. `INCONCLUSIVE`는 성공이 아니다.
- 필수 기계 검사 통과는 `REVIEW_READY`. 사람 확인이 필요하면 `pending`이며 최종 납품 PASS가 아니다.
- 전달 결과는 `DELIVERED_UNMERGED / INTEGRATED / DECLINED / STALE_SUPERSEDED`로 기록한다. 뒤 두 결과는 성공 납품이 아니다.

[실행 보고서](Templates/실행보고서.md)에 계약·후보·원시 증거·실패·재시도·미검증 사항을 연결한다. 비용은 실측/추정/미확인을 구별하고 미확인은 0으로 쓰지 않는다. 사람 활동 시간과 경과 시간도 분리한다. 게임 기능의 완료는 필요한 [사람 플레이 기록](Templates/플레이확인.md)까지 갖춰야 한다.

## 5. 기획과 지식 유지

- 기획 결정은 `Decisions.md`의 D-번호와 해당 기획의 변경 이력에 남긴다. 모든 코드 수정에 새 기획 결정을 만들 필요는 없다.
- 새 노트는 추가하고 기존 `Notes/`와 `Design/_원문/`은 역사 자료로 보존한다.
- 바뀐 판단은 새 결정으로 대체하고 옛 줄은 지우지 않는다.
- 기능 사용법은 `Features/`, 실행 근거는 `Runs/<run-id>/`, 기존 산출물은 `Archive/`에 둔다.
- 코드·씬과 문서가 다르면 원인을 조사한다. 승인된 게임 의도를 임의로 바꿔 문서와 맞추지 않는다.
- [현황](현황.md)에서 마감 영향과 작업을 막는 문제를 우선 확인한다.

## 6. 개선과 운영 버전

[자기개선 절차](자기개선.md)를 따른다. 실행 기록에서 실제 손실을 고르고 관측·원인 가설·반대 가설·바꾸지 않는 대안을 비교한다. 후보는 `Improvements/<id>/candidate/`에 두고 활성 지침·검증기·스킬에 직접 연결하지 않는다.

운영 지침·검증기·필수 테스트·합격 기준 변경은 별도 개선 범위로 다룬다. 현재 요청처럼 워크플로우 교체를 명시적으로 지시했다면 그 범위의 구현·검증을 진행한다. 기능 작업 도중 스스로 권한이나 합격 기준을 확대하지 않는다.

검토한 정확한 버전만 다음 작업에 적용하고 이전 버전·복구 방법을 남긴다. `workflow.lock.json`은 실제 파일 해시와 비교하는 버전 기록이며 접근 권한 장치가 아니다. 같은 계정에서 실행하는 MVP의 증거는 강한 격리나 독립 보안 검증으로 주장하지 않는다.

## 7. Git과 외부 효과

사용자가 요청한 행위만 수행한다. 워크플로우가 끝났다는 이유로 stage·commit·push·merge·외부 업로드·출시를 자동 실행하지 않는다. 기존 요청에서 이미 허가한 정확한 행위는 반복해서 묻지 않는다.

- `git reset --hard`, `git clean`, 강제 push, `--no-verify`를 임의로 사용하지 않는다.
- 커밋 시 저장소·브랜치·변경 범위·검증 결과를 확인하고 `타입: 한국어 요약`을 쓴다.
- 새 의존성·Editor/패키지·저장 호환성·권한·비용 상한 변경은 영향과 복구안을 갖춰 판단한다.
- 문서의 장기 설계만을 근거로 자동화 예약·유료 호출·별도 서비스·외부 메시지를 실행하지 않는다.
